# Domain Architecture

Version: 2026-06-09

## Domain Center

The Play Session is the central domain object.

Everything operational belongs to a Play Session:

- session players
- court count
- runtime courts generated by `court_count`
- runtime matches
- player payments
- court cost
- shuttlecock usage
- session income, expense, and profit

## Core Routes

- `/dashboard`: business overview only
- `/schedule`: play date list and creation
- `/schedule/[playDateId]`: sessions in one play date
- `/sessions/[sessionId]`: session detail, players, start/complete flow
- `/sessions/[sessionId]/runtime`: live court orchestration
- `/finance`: manual and session-generated finance transactions
- `/inventory`: shuttlecock product, stock, movement management
- `/settings`: browser-local operational settings

## Domain Entities

`play_dates`

- one calendar date
- unique `play_date`
- optional title and note
- title may be auto-generated as `Thứ ... | YYYY-MM-DD`
- cannot be created in the past
- cannot duplicate an existing `play_date`
- can only be deleted when not in the past and when it has no sessions
- list order is newest play date first

`play_sessions`

- one operational session
- stores time range, `court_count`, status, completion cost fields, shuttlecock product id/name, and profit aggregates
- UI status normalizes to `PENDING`, `ACTIVE`, `COMPLETED`, `CANCELLED`
- database currently stores main statuses as `NOT_STARTED`, `LIVE`, `FINISHED`
- list order inside a play date is earliest start time first
- structural edits and deletes are allowed only before the session starts and only for non-past play dates
- starting a session requires at least `court_count * 6` players

`session_players`

- session-scoped participants
- not global users
- owns payment fields and runtime status

`runtime_courts`

- current-state court snapshots by `session_id` and `court_number`
- there is no required standalone `courts` business table in the current runtime flow
- empty court rows can be generated from `play_sessions.court_count`

`runtime_matches`

- current-state queued or court-bound match snapshots
- queued suggestions use `queue_order` and no `court_number`
- court matches use `court_number`
- teams are JSON arrays

`match_histories` and `match_history_players`

- post-match lookup records created after a match ends
- support history browsing and filtering by session player
- not the live runtime source of truth
- not an event-sourcing replacement for `runtime_courts` or `runtime_matches`

`session_transactions`

- lightweight finance records
- can be manual or generated from session completion
- `session_id` is optional because manual finance can exist outside one session
- manual Thu chi currently accepts title, income/expense type, category Cầu/Sân/Khác, quantity, unit price, and note
- report views filter by selected month/year and sort newest/oldest

`shuttlecock_products`, `shuttlecock_inventory`, `shuttlecock_movements`

- product catalog, current stock, and immutable stock movements
- all inventory changes must create movements
- products can be added/edited/deleted only when stock history rules allow it
- inventory UI supports collapsed product form and collapsed import/outbound forms
- stock reports show current tubes/balls, stock value, sale amount, and play-usage cost by period

`settings`

- currently browser-local through `localStorage`
- controls auto-created completion vouchers and maximum court count per session
- not a database-backed enterprise configuration module

## Boundary Rule

Live scheduling behavior belongs only to `/sessions/[sessionId]/runtime`. Finance, inventory, settings, and dashboard must not take over live court orchestration.
